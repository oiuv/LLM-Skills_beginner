# Skill 创建最佳实践

> 本章目标：掌握从零设计一个高质量 Skill 的完整流程，包括需求分析、触发描述设计、工作流规划和迭代优化。

---

## 1. Skill 设计流程

### 1.1 四步设计法

```
┌─────────────────────────────────────────────────────────────┐
│                    Skill 设计四步法                         │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  Step 1: 需求分析                                           │
│    └── 这个任务值得封装吗？                                  │
│    └── 用户使用场景是什么？                                  │
│    └── 输入输出格式是什么？                                  │
│                                                              │
│  Step 2: 触发描述设计                                       │
│    └── 什么情况下应该触发？                                  │
│    └── 如何让用户容易发现？                                  │
│    └── 避免误触发和漏触发                                    │
│                                                              │
│  Step 3: 工作流规划                                         │
│    └── 任务分解为步骤                                        │
│    └── 确定需要的工具                                        │
│    └── 定义输出格式                                          │
│                                                              │
│  Step 4: 迭代优化                                           │
│    └── 编写测试用例                                          │
│    └── 运行对比评估                                          │
│    └── 根据反馈改进                                          │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 需求分析：值得封装吗？

**适合封装成 Skill 的任务特征：**

| 特征 | 说明 | 示例 |
|------|------|------|
| **重复性** | 需要多次执行类似任务 | 生成绘画提示词、代码审查 |
| **复杂性** | 多步骤，需要特定流程 | 数据分析、报告生成 |
| **领域性** | 需要专业知识 | 法律文档、医学术语 |
| **一致性** | 需要统一输出格式 | API 文档、测试用例 |

**不适合封装的情况：**
- 一次性任务
- 过于简单的单步操作
- 高度依赖上下文，无法标准化

## 2. 触发描述设计（最关键）

### 2.1 为什么触发描述最重要？

```
用户说了一句话
      ↓
AI 看到所有可用 Skills
      ↓
根据 description 决定是否加载
      ↓
加载正确的 Skill → 任务成功
加载错误的 Skill → 任务失败
```

**触发描述是 Skill 的"入口"**，决定了：
- 用户能否发现这个 Skill
- AI 能否在正确场景使用
- 避免误触发和漏触发

### 2.2 触发描述设计原则

#### 原则 1：明确功能 + 触发场景

```yaml
# ❌ 不好的描述
"帮助用户写代码"

# ✅ 好的描述
"代码审查专家。当用户需要审查代码、检查代码质量、
发现潜在 bug、优化代码结构时使用。支持多种编程语言。"
```

#### 原则 2：包含关键词 + 同义词

```yaml
# ❌ 只有关键词
code review, lint, bug fix

# ✅ 自然语言 + 关键词
"代码审查专家。当用户提到 code review、审查代码、
检查代码质量、发现 bug、代码优化、重构建议等时使用。"
```

#### 原则 3：主动推荐（避免漏触发）

```yaml
# ❌ 被动等待
"用于生成绘画提示词"

# ✅ 主动推荐
"AI绘画提示词生成专家。当用户想要生成AI绘画提示词、
优化现有提示词、将概念转换为 Midjourney/Stable Diffusion 
格式时使用。即使是很简单的描述如'一只猫'，
也应该使用此技能生成详细提示词。"
```

#### 原则 4：边界清晰（避免误触发）

```yaml
# ❌ 边界模糊
"帮助用户处理图片"

# ✅ 边界清晰
"AI绘画提示词生成专家。专注于生成文本描述用于AI绘画生成，
不处理图片编辑、图片分析、图片格式转换等任务。"
```

### 2.3 触发描述模板

```yaml
---
name: skill-name
description: |
  【一句话功能定位】
  
  【详细触发场景】
  当用户...时使用。包括但不限于：
  - 场景1
  - 场景2
  - 场景3
  
  【主动推荐】
  即使是...也应该使用此技能。
  
  【边界说明】
  不适用于...等场景。
---
```

### 2.4 实际案例分析

**案例：prompt-craft Skill**

```yaml
---
name: prompt-craft
description: |
  AI绘画提示词生成专家。
  
  当用户想要生成AI绘画提示词、优化现有提示词、
  将概念转换为 Midjourney/Stable Diffusion/Flux 等格式的详细描述时使用。
  
  触发场景包括但不限于：
  - "帮我生成...的绘画提示词"
  - "我想画..."
  - "用 Midjourney/Stable Diffusion 生成..."
  - "优化这个提示词..."
  - "把...转换成AI绘画描述"
  - "写个 prompt..."
  - "AI绘画..."
  - "生成图片..."
  
  即使是很简单的描述如"一只猫"，也应该使用此技能生成详细的绘画提示词。
---
```

**分析：**
- ✅ 明确功能定位
- ✅ 列举具体触发词
- ✅ 主动推荐（简单输入也要用）
- ✅ 边界隐含（专注于文本生成，不处理图片编辑）

## 3. 工作流规划

### 3.1 工作流设计原则

```
┌─────────────────────────────────────────────────────────────┐
│                    工作流设计原则                           │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  1. 步骤清晰                                                 │
│     └── 每个步骤有明确输入输出                               │
│     └── 步骤之间有逻辑顺序                                   │
│                                                              │
│  2. 工具明确                                                 │
│     └── 列出需要的工具                                       │
│     └── 说明工具使用时机                                     │
│                                                              │
│  3. 输出可预期                                               │
│     └── 定义输出格式                                         │
│     └── 提供示例                                             │
│                                                              │
│  4. 容错处理                                                 │
│     └── 异常情况处理                                         │
│     └── 回退方案                                             │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

## 4. 完整 Skill 示例

### 4.1 代码审查 Skill

```markdown
---
name: code-reviewer
description: |
  代码审查专家。当用户需要审查代码、检查代码质量、
  发现潜在 bug、优化代码结构、进行代码评审时使用。
  
  触发场景包括：
  - "帮我审查这段代码"
  - "这段代码有什么问题"
  - "代码评审"
  - "检查代码质量"
  - "优化这段代码"
  - "code review"
  
  支持多种编程语言，提供具体的改进建议和最佳实践指导。
---

# Code Reviewer - 代码审查专家

## 工作流程

### Step 1: 代码分析
- 识别编程语言
- 理解代码功能
- 分析代码结构

### Step 2: 问题检查
检查以下方面：
- **正确性**: 逻辑错误、边界条件、异常处理
- **可读性**: 命名、注释、格式、复杂度
- **性能**: 算法复杂度、资源使用、优化机会
- **安全性**: 注入风险、敏感信息、权限问题
- **最佳实践**: 设计模式、代码规范、语言特性

### Step 3: 生成报告
- 问题分类和优先级
- 具体改进建议
- 重构示例代码

## 输出格式

### 审查摘要
- 代码功能概述
- 整体质量评分
- 主要问题数量

### 详细问题列表
| 行号 | 严重程度 | 类别 | 问题描述 | 建议 |
|------|----------|------|----------|------|
| ... | ... | ... | ... | ... |

### 改进建议
1. [具体建议]
2. [重构示例]

### 正面反馈
- [代码中的优点]
```

## 5. 常见陷阱与解决方案

### 陷阱 1：触发描述过于宽泛

```yaml
# ❌ 问题：什么都会触发，导致误触发
description: "帮助用户处理各种任务"

# ✅ 解决：明确边界
description: |
  代码审查专家。专注于代码质量检查，
  不处理需求分析、架构设计、项目管理等任务。
```

### 陷阱 2：工作流步骤不清晰

```markdown
# ❌ 问题：步骤模糊
## 工作流程
1. 分析代码
2. 检查问题
3. 输出结果

# ✅ 解决：明确输入输出
## 工作流程
### Step 1: 代码分析
**输入**: 代码文件路径或代码内容
**处理**: 使用 file_read 读取代码，识别语言类型
**输出**: 代码结构摘要

### Step 2: 问题检查
**输入**: 代码结构摘要
**处理**: 按正确性、可读性、性能、安全性检查
**输出**: 问题列表
```

### 陷阱 3：输出格式不统一

```markdown
# ❌ 问题：每次输出格式不同
有时输出纯文本，有时输出表格，有时输出列表

# ✅ 解决：定义标准格式
## 输出格式

### 固定结构
1. 审查摘要
2. 详细问题列表（表格）
3. 改进建议
4. 正面反馈

### 模板示例
[提供完整示例]
```

### 陷阱 4：忽略异常处理

```markdown
# ❌ 问题：没有错误处理
## 工作流程
1. 读取文件
2. 分析代码

# ✅ 解决：添加异常处理
## 工作流程
### Step 1: 读取代码
**正常流程**: 使用 file_read 读取文件
**异常处理**: 
  - 文件不存在 → 提示用户提供正确路径
  - 文件太大 → 建议分段审查
  - 二进制文件 → 提示只支持文本代码文件
```

## 6. 快速检查清单

创建 Skill 前，检查以下问题：

### 需求分析
- [ ] 这个任务会被重复使用吗？
- [ ] 任务有明确的输入输出吗？
- [ ] 任务需要特定领域知识吗？
- [ ] 输出需要保持一致性吗？

### 触发描述
- [ ] 描述包含功能定位吗？
- [ ] 列举了具体触发场景吗？
- [ ] 包含关键词和同义词吗？
- [ ] 有主动推荐语句吗？
- [ ] 边界清晰吗？

### 工作流
- [ ] 步骤有明确输入输出吗？
- [ ] 工具使用时机明确吗？
- [ ] 输出格式定义了吗？
- [ ] 有示例吗？
- [ ] 考虑异常处理了吗？

### 质量检查
- [ ] 描述长度适中（100-300字）吗？
- [ ] 工作流步骤不超过 5 步吗？
- [ ] 输出格式可预期吗？
- [ ] 有测试用例吗？

## 7. 练习：设计一个 Skill

**任务**：设计一个 "API 文档生成器" Skill

**要求**：
1. 分析需求：为什么需要这个 Skill？
2. 设计触发描述：什么情况下触发？
3. 规划工作流：需要哪些步骤？
4. 定义输出格式：文档应该包含什么？

**参考答案框架**：

```yaml
---
name: api-doc-generator
description: |
  API 文档自动生成专家。当用户需要为代码生成 API 文档、
  创建接口文档、生成 OpenAPI/Swagger 文档时使用。
  
  触发场景：
  - "为这段代码生成 API 文档"
  - "创建接口文档"
  - "生成 Swagger 文档"
  - "API documentation"
  
  支持从代码注释、类型定义、路由定义自动生成文档。
---

## 工作流程

### Step 1: 代码分析
识别 API 端点、参数、返回值

### Step 2: 文档生成
生成 OpenAPI 格式文档

### Step 3: 格式输出
输出 Markdown / YAML / JSON 格式

## 输出格式

### OpenAPI 规范
```yaml
openapi: 3.0.0
paths:
  /endpoint:
    get:
      summary: ...
      parameters: ...
      responses: ...
```

### Markdown 文档
## API 端点
...
```
